# 交给 Codex 的执行任务

本文件是待执行任务，不表示仓库已有对应runner，也不代表已获准收费调用。

## 任务目标

阅读同包实验设计与评分规范，针对 `TobeALeg/worket` 建立可重复的抽取质量实验。先搭建和验证评测，再迭代算法。只优化用户需求完整记录、语义准确、信息有用和低人工修订负担；不要集成 Jev，不扩展为全新的知识管理/Agent平台。

## Phase 0：核验与冻结

核对本地repo与分支，保存 `git status`、完整commit、依赖锁文件、提示词、模型实际版本、token上限、分块策略和运行环境。默认比较当前产品真实代码，不另写“理想版Worket”假扮基线。

本次设计引用默认分支查询结果 `f8758f10b05984cb378d9a270a51d7386a155c53`。正式运行时再次确认；不要直接覆盖用户尚未提交的工作。实验分支/独立工作树由现有授权决定，禁止擅自push或merge。

先确定真实接入点：

- `src/extractor/openai-compatible-extractor.ts` 的提取路径。
- 核心实际应用 `WorkStatePatch` 的路径，以及实际导出交接包的路径。
- `server/workflow.mjs` 的 `extractDefinition()` 及其校验逻辑。

不修改用户全局hooks或真实工作库。使用隔离副本、授权快照和脱敏日志。没有配置可调用模型/费用授权时，只构建离线评测和mock结构自测。

## Phase 1：数据合同与人工确认点

实现 input manifest：case、来源快照哈希、work/event关系、检查点、合法附件内容、任务家族、作者匿名ID、split。

实现 gold manifest：遵循评分规范；gold不挂载到被测抽取器或下游执行者的目录/环境。开发Agent只能访问开发材料；验证/封存评分由独立流程访问。

人工关卡：

- H0：哪些真实资料、哪些接收服务、何种用途、多少费用被授权。
- H1：gold、关键性、有用性判断与阈值冻结。
- H2：入围首稿的真实用户修改与计时。
- H3：确认版业务验收、最终方法选择和对外结论。

未知授权/预算必须阻断live调用。当前附带配置 `live_enabled=false`、预算为空，是刻意的安全默认，不允许自动填0元通过。

## Phase 2：runner、trace与grader

建议新增隔离目录（最终名称可按仓库习惯调整）：

```
evals/extraction/
  adapters/        # 当前路径与候选路径；相同产品出口
  fixtures/        # synthetic 与 authorized-real 分开
  manifests/       # 快照、配置与数据划分
  graders/         # 确定性检查 + 经人工校准的语义对齐
  prompts/        # 版本化实验变体
  runs/           # 不覆盖的原始结果，敏感数据默认不入git
  reports/        # 分子分母、差值、修改负担、失败
```

这是建议结构，不是现有目录存在性的声明。

每次trial保存：run_id、case_id、track、cutoff、configuration、repeat、全部实际模型请求和原始回复（不要求或诱导记录隐藏推理）、真实usage、time、候选/协调/投影快照、程序校验结果、实际持久化状态、交接/Definition导出、错误及重试关系。

保存自然产生的工具执行日志，但不要把事件里未公开的隐藏思维当作抽取材料。敏感内容日志加访问边界，报告只展示脱敏必要证据。

runner能力验收：

- dry-run不调用provider；未授权、预算不明或上限超出阻断。
- 每个case/trial均落账，失败不能漏报。
- run不可覆盖；重试生成新id并保留 retry_of。
- schema/证据/参考规则变化会改变hash并使旧审批失效。
- mock和synthetic不可标real。
- 仅来源ID真实但不支持含义的内容不能判正确。
- 对照组使用同样的产品出口与展示条件。
- 人工计时未知为null，不从Agent运行时间推断。
- 外部评分成本与实际产品抽取成本分别记。

完成后跑 `02_评分与人工验收.md` 的评分器反作弊用例。此包JSON只提供配置/示例，不附带已经完成的生产runner；不得把“成功解析JSON”说成语义测试通过。

## Phase 3：E0与最小算法对照

先用开发集接真实路径建立A0基线，定位错误发生在哪个阶段。无候选观测点的旧路径标 `NOT_OBSERVABLE`，不要另调LLM伪造其内部状态。

做E1：先只改提示词，再只改上下文组织。每次保存diff和假设。发现实际丢失在程序持久化/导出而不是LLM时，先补回归并修该层，不以增加提示词掩盖。

随后做E2四格对照；任何无法在某条路径实际改变输入的因素标“不适用”，不算有意义样本。所有变体保持最终产品schema和人工权限边界；必要中间schema留在适配层。

## Phase 4：按错误决定追加实验

E3用于仍存在的漏项/误提，不默认加大量审核。R1/R2匹配审核资源预算。

E4用于噪音/去重/范围投影，固定上游候选避免把抽取差异混成压缩收益。

记录有效需求从原文→候选→协调→最终视图→实际导出的路径，以及删除/降级/待确认理由。原文保留不能替代当前视图召回。

每个开发循环最多3轮；连续2轮无实质改善停止，输出失败分析。禁止自动访问封存集继续修prompt。

## Phase 5：稳定性、人工评审和业务探针

仅入围方案与基线做E5/E6。预生成随机顺序和trial清单，固定所有合法材料、环境、模型和权限。

所有人机结果保留raw/confirmed两套。人工新增知识与历史遗漏修复分开标注。工作完成或Definition正式发布必须由实际产品权限和人工确认决定，不能让runner签字。

下游任务用新的输入值，检查错误旧值继承；只能声称所测试任务家族内的效果。普通总结必须认真制作，不故意删减关键来源形成弱对照。

## Phase 6：交付物

1. 可重复runner及其结构/失败路径自测；真实路径接入说明。
2. 冻结的baseline、实验变体、模型/提示词/输入/评分版本清单。
3. 开发/验证/最终封存manifest与访问隔离证据。
4. 带来源和人工裁定的gold；有分歧项不隐藏。
5. 全部trial明细与失败，不仅成功列表。
6. 首稿/确认版差异、实际人工计时与不确定值。
7. 结果报告：推荐哪种方法、相对谁、改善多少、代价是什么、在哪些案例退步、什么还未知。

推荐算法必须通过预注册门槛。若没有方案胜出，交付“无明确胜者+错误分布+下一步最小验证”，而不是强行宣布多阶段胜出。

## 角色分工

最小两个工程/评测角色加用户业务判断即可。工程Agent只改实现；评测Agent维护runner和只读评分，不能迁就被测结果修改标准；用户裁定真实意图、有用性与最终业务结果。需要额外审计时第三Agent只查泄漏、评分器与账目。

不能声称多个Agent的投票等于独立人类证据，也不能将任务控制Agent的工作时长冒充用户劳动时间。
