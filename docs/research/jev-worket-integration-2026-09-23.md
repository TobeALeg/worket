# Jev 在 Worket 中承担哪些判断

日期：2026-09-23。状态：研究与设计建议，未批准实现、未调用 API、未上传工作记录。用户问“提取与传递涉及很多判断，接入 Jev 会是什么样”。官方接口与限制核查见 [API 事实](jev-api-facts-2026-09-23.md)。

## 判断

Jev 适合作为可替换的语义判断 Adapter：对固定证据范围中的候选要求、关系或接续结论，回答有限选项的问题。它可以服务提炼与接续，但不直接替代候选生成、来源存储、工作包生成、确定性规则或用户确认。官方说明 Jev 不生成正文、代码或对话，而是对 state 和 typed questions 返回结构化答案。[官方定位](https://docs.typesafe.ai/introduction/coding-agents)

当前 Jev 1.13 对中文/CJK 明确较弱，Worket 又以中文对话提炼为主；因此架构适配并不等于应该全面采用。先旁路验证原始中文样本，比较错误率、审阅量和总成本，再决定是否用于特定判断。[语言支持](https://docs.typesafe.ai/models#language-support)

## 建议路径

```text
已授权原文 + 已确认规则 + 本次材料版本
  → 程序准备可追溯证据；LLM 提出原子候选及来源
  → 程序检查格式、引用、材料 hash、版本和关系目标
  → Jev 检查证据支持、采用范围、规则关系等语义
  → 程序检查回答之间是否矛盾，并按风险/验证过的阈值分流
       ├─ 可用判断 → 本次状态候选 / 定义草稿
       └─ 不充分、冲突、超时或低把握 → 补证据 / 深度模型 / 人工审阅
  → 本次继续保持 workId；发布长期规则仍需用户确认
```

模型生成候选与 Jev 判断需要同一批原始证据、相邻上下文、已有规则及版本。只给候选摘要会让第二个模型重复第一个模型的遗漏。即使所有候选通过，仍可能缺少一条根本未被抽出的要求；候选正确率与来源要求覆盖率必须分开评估。

## 共用的小问题

下表的选项是 Worket 拟议的内部语义，不是 Jev 的内置领域能力；每项实际效果均待测。

| 判断 | 可提供的候选答案 | 消费位置 |
| --- | --- | --- |
| 原文是否支持该候选 | 支持 / 相反 / 未涉及 / 证据不足 | 定义与接续的来源复核 |
| 这条要求的适用范围 | 本次实例 / 同类后续工作 / 不确定 | Definition 与 InstanceOverride 分流 |
| 对这条原子提案是否有明确采纳 | 采纳 / 拒绝 / 尚未决定 / 证据不足 | 用户发言与 Agent 提议的区分 |
| 与指定旧规则是什么关系 | 等义重复 / 补充 / 替代 / 冲突 / 无关 / 不确定 | 要求协调，结合范围决定影响哪一层 |
| 记录支持哪种完成程度 | 尚未完成 / 仅自报完成 / 有适用检查证据 / 证据不足 | 阶段进展候选；用户验收单独处理 |
| 候选下一步是否符合当前范围 | 适用 / 与证据冲突 / 证据不足 | 交接前复核 |

发言者是谁、摘录是否存在、文件 hash 是否一致、deliveryId 是否匹配、依赖图是否有环等已有确定答案，继续交给程序。Jev 评估的是证据含义，不会实际检查文件系统、运行测试或证明外部 Agent 已完成工作。

一条消息包含多个义务时先拆为候选原子要求，再按要求判断，避免对整段“好”作整体采用判断。阶段候选中必须容纳“当前没有唯一阶段/候选不全”，不能强迫在已有阶段里选一个。

## 具体例子

已确认定义 r1：“视频口播不超过 50 字。”新消息 e1：“这次可以到 80 字，以后仍按 50 字。”

候选生成保留两个作用范围及 e1；程序核对 e1 和 r1 的版本。Jev 可分别判断“80 字是否仅本次”“是否明确要求长期改变”“原文是否支持该解释”。假设这些判断与证据一致，Worket 才能生成实例的 80 字覆盖候选，长期 r1 保持 50 字。同一实例中途交接消费实例覆盖；下次新建实例消费长期定义。

这里的期望是人为设定的验收答案，不是已经得到的 Jev 响应。用户对长期规则的发布确认不因模型高置信而被省略。

## 接入现有实现

第一步先在 [server/workflow.mjs](../../server/workflow.mjs) 的聚合结果经过结构/来源校验之后，为原子候选调用复核 Adapter；不在纯函数 validateResult/effectiveRules 内插入网络调用。第一轮只记录 verdict、原始 probabilities/confidence、输入摘要、模型版本、问题版本和来源版本，不改现有发布行为。

后续通过中文评测后，再让 [ContinuationService](../../src/handoff/continuation.ts) 使用同一个判断契约复核阶段候选；生成器仍提出阶段及关系，Jev 对窄问题评估，依赖关系与材料版本由程序验证。现有 [v3 交付入口和模型连接缺口](../reviews/2026-09-23-work-object-audit.md) 必须另行修复，接入 Jev 本身不会解决它们。

模型 Adapter 放在既有后台，供应商凭据留在服务端。将发送到新增服务的正文范围纳入现有云端处理授权与配置核对；当前讨论不授权上传用户历史。持久判断以证据快照、候选和模型/问题版本为缓存依据，材料或来源改变后失效；不让历史 judgment 变成永久事实。

## 批量问题与不确定性

官方允许在同一 state 中批量提出独立问题。若 B 的问题必须使用 A 的答案，则由代码分两阶段；同批回答不能假定互相看见。候选很多时先用来源、规则类别和范围缩小需比较的对象，避免无条件对全部规则做两两模型判断。[问题与组合](https://docs.typesafe.ai/introduction)

Choice/Score 的 confidence 来自答案分布，不是来源充分性证明、用户授权或本任务上的正确率。Noul 没有相同的独立 confidence 字段。保留“不确定/无匹配”选项，并用 Worket 标注样本选择阈值；不照搬示例数值。[Confidence](https://docs.typesafe.ai/confidence)

官方引用核验范例把原文匹配交给程序，再让 Choice 判断该段是否支持候选主张，适合借鉴为第一个窄切入点。[引用核验](https://docs.typesafe.ai/cookbooks/citation_check) 官方也演示了小模型提取、Jev 检查、必要时升级推理模型的流程，但其案例结果不能推算为 Worket 的节约比例。[提取分级流程](https://docs.typesafe.ai/cookbooks/sde_cascade)

## 最小试验

先比较“现有提取”与“同一批提取结果 + Jev 旁路复核”，固定输入和候选，隔离检验判断层是否增益，再考虑改变生成器。使用项目现有的部分采纳、单次豁免、取消强制/新增禁止、规则替代、否定完成、来源修订样本，并增加未参与调参的中文案例。中文原文保留；改用英文问法或翻译属于另一组实验，不假设翻译必然提高质量。

逐类看错误放行、错误阻拦、未决比例、来源漏项、用户审阅时间、总延迟与费用。错误把一次例外升级为长期要求，应独立报告，不能被大量简单样本的平均分掩盖。记录 Jev 与生成模型的共同误判；两模型同意并不自动构成独立验证。

可验证的目标是减少需要人工反复理解的语义分歧，同时保持原文可回查与用户最终决定。该目标尚未通过 API 或业务试验证实。
