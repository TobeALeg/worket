# 从会话到工作要求：Worket 研究实验

研究日期：2026-09-10 起。研究分支：`codex/conversation-requirements-research`。这是独立算法实验，不是应用新增功能、正式工作定义发布或用户验收。

## 研究问题与范围

用户的出发点是：人机协作的效果不仅取决于 Agent 执行能力，也取决于人类是否表达了足够明确的工作要求。我们研究能否从真实协作中的要求、纠正、否定和确认，恢复一份可供执行者使用的工作要求，并指出真正需要补充的决定。

本实验交付可运行代码、真实 API 调用记录和评估。目标是本次 WorkInstance 的要求候选；跨实例归纳为稳定 WorkDefinition 仍需要单独的适用性判断和用户确认。不能把本次工作中的客户信息、临时授权或例外直接提升为可复用定义。

## 模型身份与研究依据

用户最初指定 DeepSeek V4 Flash。2026-09-10 实测请求 `deepseek-v4-flash` 返回 `deepseek-flash`；官方同日公告说明旧 V4 Flash 已退役，其别名转向 V4.1 Flash。告知用户后，用户明确同意改用 V4.1 Flash。因此下文实验均标注 **DeepSeek V4.1 Flash**，不称为 V4 Flash 原版结果。[官方变更说明](https://api-docs.deepseek.com/updates/)

本地使用 Node.js 24.15.0，无额外运行时依赖；API Key 仅从进程环境读取。记录请求名、返回名、日期、响应 ID、用量、算法版本和代码哈希。服务端模型别名可能未来更新，记录标识不等于能够冻结远程权重。

ToM-SWE 提供的启发是：把理解用户目标与约束作为独立职责，采用分层分析并回查原始证据。其输出主要服务用户建模和编码 Agent 建议，不直接对应 WorkDefinition。[ToM-SWE v2](https://arxiv.org/html/2510.21903v2)

Ambig-SWE、ClarifyCodeBench 启发我们将要求缺失、澄清和下游交付分开评估。我们没有运行它们的原始题库或排行榜；自建难例和纯数据下游实验只借鉴评测问题。详见 [研究依据与拟议协议](conversation-requirements-benchmarks.md)。

## Work Object 架构

工作身份由 WorkInstance 决定，会话只是来源；同一工作可以跨会话和执行者。导入器默认生成独立工作 ID，调用方也可传入既有实例 ID。会话 ID 只留在来源与执行片段信息中。

```text
WorkInstance
  ├── WorkRecord：有序、可见消息及不可变快照哈希
  ├── WorkAnalysisRun：处理这份记录的一次模型运行
  └── WorkRequirementsDraft：要求、证据、变更历史和待澄清项
         └── WorkExecutionRun：实验执行器使用这些要求产生交付
```

候选的 ACTIVE 表示在候选中当前有效，不表示 Worket 用户已经审阅发布。输出状态为 READY_FOR_REVIEW 或 NEEDS_CLARIFICATION。`USER_CONFIRMED` 只指原会话中某项提案被用户确认；程序要求其提案证据早于确认消息。候选和运行均引用原工作与来源，不产生独立用户画像或 Agent 自主权限。

代码入口是 `extractRequirements(record, provider, options)`；运行、模型调用、原文定位和语义处理分别封装。没有修改产品数据库、UI 或应用沉淀服务，保留现有 `WorkDefinition → WorkInstance → WorkRecord` 关系。[实现说明](../../experiments/conversation-requirements/README.md)

## 算法及开发中发现的问题

最初实现是直接提取基线和“分块证据 → 工作整合 → 原文审阅”的 ToM 式流程。真实样本促使我们逐步改进：

1. **引用由程序管理。** 模型复述引用时会删除 Markdown、空格或路径。改为程序将完整消息切成带编号和位置的片段，模型选择编号，程序还原原文。字面存在、偏移、角色和工作身份可以机械验证；语义支持仍需评估。
2. **区分用户要求与助手方案。** 助手的技术解释、已经完成的实现、合理建议，不自动成为用户约定。用户提问也不能被转换成助手答案对应的要求。混合了用户结果要求与未确认实现细节的条目应拆开或收缩。
3. **恢复明确确认的范围。** “其他都同意，只有这些点改”不同于“收到”。前者需要回到此前提案逐点计算确认与排除范围。忽略这一点会漏掉整组要求。
4. **把投诉当作工作信号。** 在进行中的实现任务里，“现在还是不能识别”通常是在要求修复，不应只保留成历史事实。
5. **将未决问题控制在影响交付的范围。** 不要求用户重新确认已作出的选择，不让使用者回答本应由执行者调查的内部 API 问题。
6. **失败显式保存。** JSON 语法重试与契约修复都记录调用和用量；无法通过校验不生成伪成功。程序只修补无语义的默认字段或原文定位，不自行补写用户要求。

最终提供 `audited` 保守模式：直接提取 → 原文重建 → 结构校验及至多一次修复 → 来源支持分类。最后一步模型只判定支持程度，程序可将条目降为 INFERRED/UNRESOLVED、去掉已回答的问题或降低全局阻塞级别，不能新增已获授权的要求。分类也可能出错；它提供一层审阅辅助，不构成准确性保证。语义分类放在结构修复之后，防止修复步骤绕过它。所有变化保留运行记录。

`direct`、`structured`、`verified`、`grounded`、`audited` 均保留供消融和复查。最终默认是 low 思考预算；这源于本轮开发观察，不是对其他任务的通用建议。CLI 默认与批量评测历史默认有区别，复现时按下列显式参数调用。

## 数据与评估限制

合成集由 Codex 自主编写，12 条开发样本、8 条预先冻结的测试样本，覆盖纠正、部分确认、例外、冲突、引用指令、工具注入、长上下文及任务边界。它们不是公开 benchmark 原题，也不是盲测：作者知道题目主题，但最终测试未用于提示调优。

真实集来自用户明确授权的本机 Codex 会话，先选择 6 项工作，3 项用于开发，另 3 项留出。它们来自同一个用户，不能支持跨用户泛化结论。工作领域包含软件产品要求、更新流程、品牌视觉和视频制作。仅导入可见用户/助手文字；不读取内部推理、系统提示、审批子任务、子代理通知或附件内容。

原始会话、脱敏副本、gold 和逐条真实输出留在本地忽略目录。常见密钥、邮箱及本机用户名被脱敏，不能保证自动识别所有商业信息；用户授权了本机记录用于本次验证，并未据此扩大产品的数据采集行为。

Gold 由 Codex 依据来源编写，开发阶段发现覆盖不足后扩充，并保留旧版本。辅助语义评分使用独立提示调用 DeepSeek；生成模型和评审模型仍相同。Codex 的逐条复核也属于模型评估，不是使用者本人或独立人类标注。报告不能把自动评分全通过当作用户验收。

指标分别统计：正向要求与必要澄清覆盖、禁错项、有效条目的来源支持、多余问题、契约失败和调用用量。分母包括失败样本，不能只报告成功输出的百分比。要求召回不能由原文引用存在率替代。


## 前瞻留出结果：v0.9，之后未覆盖原产物

最终提示冻结后，用相同模型、thinking enabled、reasoning_effort=low 运行此前未调优的 8 条合成与 3 条真实样本。两组信息输入相同，grounded 多一次来源核验；**调用预算不相等**，不是等计算量比较。每组只运行一次，未估计随机波动或置信区间。

以下为 DeepSeek 自动评分，不能解释为真人正确率：

| 数据 | 方法 | 完整返回 | 正向槽位覆盖 | 全部检查 | 无依据 ACTIVE / ACTIVE | 全项通过案例 |
| --- | --- | --- | --- | --- | --- | --- |
| 合成留出 | direct | 8/8 | 22/23 | 36/37 | 1/36 | 7/8 |
| 合成留出 | grounded | 8/8 | 23/23 | 37/37 | 0/36 | 8/8 |
| 真实留出 | direct | 3/3 | 18/19 | 21/22 | 0/25 | 2/3 |
| 真实留出 | grounded | 3/3 | 17/19 | 20/22 | 0/22 | 1/3 |

不能据此声称 grounded 稳定胜过 direct。合成难例的局部提升没有在真实小样本上复现。真实配色案例把“可以探索”错放成待确认，过度保守造成漏召回；两组视频案例都因采用后续明确同意的精简稿而被原稿 gold 判失分。Codex 原文复核认为视频修改链有依据，因此这一项属于 **gold/裁判争议**，保留原评分，不事后修订到满分。[逐条复核](conversation-requirements-semantic-audit.md)

| 留出实验 | 调用数（含评审） | 输入 token | 输出 token | 各调用耗时合计 |
| --- | ---: | ---: | ---: | ---: |
| 合成 direct | 16 | 26,619 | 38,999 | 181 秒 |
| 合成 grounded | 24 | 50,788 | 53,350 | 245 秒 |
| 真实 direct | 6 | 33,443 | 19,786 | 89 秒 |
| 真实 grounded | 9 | 58,451 | 35,822 | 160 秒 |

耗时是调用时间之和，不是并发实验的墙钟时间。输出 token 来自供应商 usage，可能含思考 token；只保存可见 JSON 答案，不保存内部推理。没有将 token 换算为固定价格，真实费用还取决于供应商当时计价与缓存。非思考、high/low 的历史比较存在版本和样本差异，只用于定位问题，不能作受控能力排名。

## 开发失败与最终保守回归

v0.1 合成 direct / verified 分别有 5/12、6/12 未完整评分；v0.2 真实 verified 有 2/3 引文复写失败。v0.4 的确认时序检查抓到了未来提案被追认，但修复引入字段错误；v0.6 仍有一次整段替换导致重复 ID；v0.7 的长对话触发输出长度上限。失败均留档，没有用重跑成功覆盖失败文件。

扩充真实开发 gold 后，v0.6 direct 的正向覆盖仅为 21/27，并有 2 个无依据 ACTIVE。v0.8 low 达到 26/27；v0.9 达到 27/27，但独立 Codex 复核仍发现“不得仅靠”变成“不得使用”、可选分支变全局阻塞、用户引用旧方案后改用新方案仍保留旧前提。这说明 **来源哈希和自动评分同时通过，也不能证明工作要求忠实**。

v0.10 尝试只可降级的支持分类，v0.11 将分类移到所有结构修复之后。它们复跑的数据都已被看过，属于回归，**没有新的未见留出**。最终回归数值与保留问题见本报告末尾的运行记录表；用户审阅仍是必要边界。

## 下游实验：要求明确性与执行能力分开

四个自主构造的订单任务有可机械判定的金额、币种、状态和日期筛选目标。每题三组：初始模糊请求、完整会话、提炼后的 ACTIVE 要求。初始组缺少后续决定，不能把它的未交付直接计成推理失败；信息相同的主要对照是完整会话。

| 执行方式 | 初始请求交付 | 完整会话交付 | 提炼要求交付 |
| --- | --- | --- | --- |
| 非思考模型直接算金额 | 0/4（4/4 要求澄清） | 2/4 | 2/4 |
| 非思考模型生成有限计划、程序计算 | 0/4（4/4 要求澄清） | 4/4 | 4/4 |

程序只执行有限字段构成的计算计划，没有执行模型生成的任意代码。直接算术的单位与加减错误说明，要求明确并不能替代可靠执行。第二组支持“提供已澄清的信息有助可交付性”的小样本观察；**未显示提炼相比完整会话的额外收益**。四题同一模板，不是真实工作复用验收，也不能外推节省多少时间。下游代码及诊断数据可复跑；使用的是早期非思考 verified 提炼，不能把其结果归到最终 audited 版本。

## 如何复现和审阅

本机只做文本处理与 API 编排，无 GPU 和本地模型训练要求。当前在 Node.js 24.15.0 实际运行；运行说明要求 Node.js 22+，未逐一测试其他 Node 版本。API Key 从环境读取，不写入仓库；需能访问配置的 HTTPS 模型服务。单记录预算 400 KB，超限显式拒绝；大量历史应按真实工作边界选择，不把全部会话拼成一个任务。

在研究 worktree 根目录运行：

```sh
# 标准 WorkRecord → JSON + Markdown + 完整运行记录
WORKET_RESEARCH_THINKING=true WORKET_RESEARCH_EFFORT=low \
  node experiments/conversation-requirements/cli.mjs output/my-work.json output/my-requirements.json audited

# 最终版本回归（这些数据已用于评估，不再是新的盲测）
WORKET_RESEARCH_THINKING=true WORKET_RESEARCH_EFFORT=low \
  node experiments/conversation-requirements/benchmark.mjs experiments/conversation-requirements/data/test.json output/my-regression audited

# 离线检查来源与程序契约
node experiments/conversation-requirements/verify-evidence.mjs output/my-work.json output/my-requirements.json
node --test experiments/conversation-requirements/test/*.test.mjs

# 独立下游诊断
node experiments/conversation-requirements/downstream.mjs output/my-downstream plan
```

公开合成来源在 `experiments/conversation-requirements/data/`；真实记录与逐条结果在本机忽略目录 `output/requirements-private/`。本轮实际 CLI 产物为 `output/requirements-private/final-cli-video.json`、同名 `.md` 和 `.run.json`，可从工作目标、来源引用、未确认内容三个角度审阅。供应商返回名已检查为 `deepseek-flash`，但远端权重未来变化仍可能导致重跑不同。

分享用的 [实验结果与调用证据](conversation-requirements-evidence.json) 保留各版本配置、代码哈希、用量、错误、评分与合成输出；去除了真实会话正文、gold 和模型回答正文。历史部分失败记录缺少完整分母时显示 null，不以成功子集冒充全样本正确率。初始真实 manifest 与扩充 rubric 都保留快照说明。

## 研究判断

这次完成的是可运行、可追溯、可供审阅的**工作要求提炼原型**。它能够恢复初始指令以外的纠正、确认和约束，能把来源、当前有效性与未决决定写成结构化产物。我认为它已适合继续进行工作要求草案实验；尚不适合直接自动发布可复用 WorkDefinition 或直接当作执行授权。

研究中最有价值的发现是：完整性不是“多写一些合理要求”，而是恢复用户实际表达的约定及其变化。以后应冻结新版本、招募多用户独立标注，并在新的 WorkInstance 上比较完整会话与候选要求的交付、修订量、重复解释和成本。跨实例泛化、真正的新工作执行与真人接受是后续独立实验，不在本次结果中冒充完成。


## 最终运行记录：v0.11（全部为已见数据回归）

| 数据 | 完整返回 | 正向槽位覆盖 | 全部检查 | 自动评审无依据 ACTIVE | 全项通过案例 |
| --- | --- | --- | --- | --- | --- |
| 3 条真实开发 | 3/3 | 26/27 | 32/33 | 1/40 | 2/3 |
| 3 条原真实留出回放 | 3/3 | 19/19 | 22/22 | 0/23 | 3/3 |
| 8 条原合成留出回放 | 8/8 | 23/23 | 37/37 | 0/36 | 8/8 |

**不要把后两行的满分当新的泛化证据。** v0.11 原文复核仍发现两个确定漏检：活动窗口样本引用早期确认，却加入后来助手提出的实现限制；沉淀样本对交接约束的支持，被扩展成对已淘汰额度等待前提的支持。支持分类器仍会把部分支持误判为整句支持。更新样本还出现将高层目标随旧实现一并降级的保守损失。完整事实、条目 ID 和快照见 [独立语义复核](conversation-requirements-semantic-audit.md)。

最终 CLI 单次视频样本耗时 27.5 秒，调用 3 次，生成 13 条要求（12 条 ACTIVE、1 条历史）、无未决问题，状态 READY_FOR_REVIEW。与批量视频结果存在措辞和拆分差异，显示同一配置仍有生成波动。独立离线检查验证了最终 14 个批量草案的 212 处原文引用、位置、哈希及工作归属，另验证 CLI 草案；这些只证明机械来源正确。15 项程序测试通过，覆盖身份隔离、来源位置、确认时序、注入来源过滤、失败分母，以及结构修复后才执行语义闸门。12 个运行模块语法检查通过。

v0.10 长样本出现一次评审覆盖不全，提炼草案已保存但评分失败；其缺失样本进入总分母，没有覆盖为成功。最终 v0.11 没有接口或契约失败，但包含上表语义失分。下游的 [24 组输出与确定性检查](conversation-requirements-downstream.json) 单独保留，避免与提炼槽位分数混算。
