# 从真实对话提取工作要求：研究依据与评测协议

核实日期：2026-09-10。本文是独立研究与拟议协议，不是论文复现结果。用户最初指定 DeepSeek V4 Flash；2026-09-10 发现官方下线并重定向后，用户确认采用 V4.1 Flash。以下为拟议协议，实际样本、模型参数和执行结果以研究报告为准。

## 一手研究给我们的启发

| 来源与核实版本 | 已核实的研究设计 | Worket 可借鉴处及边界 |
| --- | --- | --- |
| [ToM-SWE v2，2026-01-29](https://arxiv.org/html/2510.21903v2) | 会话分析、跨会话用户模型与执行中回查历史；代码任务测试与模拟用户满意度分别评估 | 借鉴分层分析与证据回查；用户画像和满意度不能替代工作要求准确性或交付验收 |
| [Ambig-SWE v3，2026-02-21](https://arxiv.org/abs/2502.13069v3)；[官方实现](https://github.com/sani903/InteractiveSWEAgents) | 区分发现要求不充分、提出针对性问题、利用回答完成代码任务；代码提供 Full/Hidden/Interaction 条件 | 将“发现缺口”“解决缺口”“完成交付”拆开；不把识别出问题就算完成任务 |
| [ClarifyCodeBench v2，2026-08-31](https://arxiv.org/abs/2607.00711v2)；[官方实现](https://github.com/fangz-cs/ClarifyCodeBench) | 419 个带关键问题/答案的任务，每轮提一个问题或输出代码；最终代码另接 LiveCodeBench 隐藏测试 | 借鉴固定答案和独立交付检查；它是编程题澄清，不能直接代表真实多轮聊天或可复用定义 |

ClarifyCodeBench 的 TKQR 奖励较早覆盖关键问题，ORA 衡量轮数与关键问题数的接近程度；实现还区别重复问题，并将最后代码轮计入部分统计。Worket 的事后抽取不包含同样的互动轮次，真实用户也可能一轮回答多个问题，所以不直接套用其分数或宣称可比。[指标源码](https://github.com/fangz-cs/ClarifyCodeBench/blob/main/clarifycodebench/metrics.py)、[交互源码](https://github.com/fangz-cs/ClarifyCodeBench/blob/main/clarifycodebench/interact.py)

以上来源没有直接验证“从用户真实聊天提炼可复用 WorkDefinition”；下述协议是针对 Worket 目标的设计建议。

## 先定义正确答案是什么

评测单位是一段有明确工作边界的对话及一个时间截点，不能在截点前的抽取中使用后来的回答。每个样本由人工标注原子要求与原文位置，明确哪些会实质改变产出。对同一时间截点，保留：

- `requirements`：目标、输入、产出、约束、决策或验收要求；含 `evidence`、`scope`、`status`。
- `changes`：替换、撤回、细化或新增要求的关系及其出处；旧要求保留历史但不能仍被当作有效要求。
- `exceptions`：临时例外及适用条件，关联其覆盖的通用规则；“这次”不能被泛化成“以后”。
- `openQuestions`：材料确实不足且会影响交付的槽位；区分未问、已问未答、回答不充分和冲突未解决。
- `nonRequirements`：尚未获用户确认的 Agent 提议、转述/引用、无关偏好及被拒绝方案，作为误提取检查对象。

同义措辞允许匹配同一个原子要求；一个宽泛句子不能自动抵扣多个细节遗漏。用户未表态的 Agent 自述不构成已确认事实。对真实性无法判定的隐含意图标为待确认，不由评测模型编造唯一答案。

## 开发与留出隔离

先建立独立的开发集、验证集、最终留出集清单与内容哈希，再修改提示词。小样本先报告逐例结果和分母，不以固定比例制造统计充分性的印象。

同一用户同类工作的续聊、改写、摘要、切片和衍生样本不得分散到开发与最终留出。通用能力按用户/工作族分组隔离；同一用户的跨次复用实验则按时间隔离，并单列结果。所有检查过答案且据此调整算法的样本都转为开发证据，最终留出只能另取。

跨次定义测试可用前两次工作形成候选，第三次完整保留，之后用新输入执行；它检查复用，不作为首次抽取的训练样本。合成样本用于覆盖边界，真实授权对话用于效果判断，二者分别统计；公开题还可能存在基础模型预训练污染，不能当作完全未知任务。

## 必须分别报告的指标

| 检查 | 可计算方式 | 防止的误判 |
| --- | --- | --- |
| 意图与关键要求遗漏 | 有效金标准要求召回率；另列每例缺失的关键要求数 | 只提取容易的几条也获得高分 |
| 无依据要求 | 缺少支持证据的输出条目 / 全部输出条目 | 内容看起来专业就当用户想要 |
| 证据正确性 | 引用存在率与“原文支持该要求”的人工判定分别计算 | 引用指向真实消息但语义不支持 |
| 纠正与有效状态 | change 关系准确率；被替换要求仍生效的数量 | 只保留最后一句或把旧新要求同时执行 |
| 例外与范围 | instance/work/global 分类混淆；例外误泛化数 | 本次特例变成永久规则 |
| 未决问题 | 必要缺口召回、误报率、擅自填答案数；无缺口样本也纳入 | 问得越多越好，或把未知写成已解决 |
| 下游结果 | 整项交付通过率、逐要求违反数、必要澄清数、成本与耗时 | 抽取文本质量替代实际完成能力 |

不汇总为一个足以掩盖关键错误的总分。每个变体输出原文、候选、人工对齐、检查日志；只用 JSON schema 或字符串规则证明结构与可定位性。语义判定可由模型辅助，但抽样人工复核、记录争议，不能让生成器独自给自己验收。

## 一个低成本、可机器执行的下游实验

选择“从订单 JSON 生成客户汇总 JSON”的纯数据交付，不运行模型生成的程序。预先手写少量固定输入和独立参考计算器：订单有 `customerId/date/status/amountCents`，要求指定日期范围、状态、金额口径、排序及输出列。聊天中分次提出这些条件，包含一次纠正、一次限定日期范围的例外、一项 Agent 未获确认的建议。

例如对话先要求按订单数排序，随后明确改成按净额降序；“这次保留零金额客户”只适用于本次。固定测试覆盖相同金额的稳定排序、边界日期、取消订单、退款和零金额客户。缺少关键口径的样本另作未决组，预先标注必须问的槽位，不给抽取器或执行器隐藏答案。

配对条件保持同一输入、执行模型、采样参数、输出限制与调用预算：A 只给原始聊天；B 原始聊天加普通摘要；C 原始聊天加结构化要求。另加 D 人工核实的要求作为诊断参考，不把它当可部署算法。可加 C-only 检查结构化结果是否能独立交接，但它与 C 的信息量不同，分开报告。

每个条件输出最终 JSON，由独立程序核查精确行集合、字段、金额、次序及每条验收要求。对未决组，正确结果应是结构化的 `needs_clarification` 和必要槽位；给出任意成品不能算完成。允许澄清的扩展实验使用固定答案表，回答后再测同样的交付检查。

先冻结样本、参考结果和评分器再运行抽取；对相同样本重复少量配对运行，逐例报告变化。关键结论是 C 相比 A/B 是否减少具体交付错误，以及哪些错误来自抽取、哪些来自执行。只有人造订单样本通过，应称“下游可执行开发实验通过”；必须补充真实工作输入及留出复用，才能判断产品效果。

本协议可在普通本机编排加模型 API 上运行，不要求搭建完整 SWE 沙箱，也不宣称复现上述论文排行榜。
