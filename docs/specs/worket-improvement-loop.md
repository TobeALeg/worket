# Worket 持续优化顺序

日期：2026-09-23。状态：用户已批准执行，持续优化 loop 已启动。当前进度与续跑入口见 [优化检查点](../acceptance/worket-improvement-loop.md)。

## 产品目标

Worket 让工作独立于聊天、Agent 和应用存在：记录用户与执行者的协作，维护本次工作状态，让同一项工作可以交接继续；从交互中的要求、纠正和确认提炼可复用 working contract，用该约定、必要 skill/固定资料和新输入开展下一次工作，并将后续修正形成有依据的演进。

交接保留同一 WorkInstance，复用创建新 WorkInstance。Work State 表达本次状态，WorkDefinition 承载通用约定，WorkRecord 保留事实。用户的长期目标是越用越少重复解释，执行者逐渐更准确地按其要求交付。当前具备主动沉淀、版本化规则和新实例链路；连续新交互与已有定义的增量协调尚未实现。

## 拟定顺序

| 顺序 | 优化方向 | 验收重点 |
| --- | --- | --- |
| 1 | 固定基线与端到端验收底座 | 冻结现有真实案例及失败；区分真实回放、合成边界、未见输入；每轮可比较 |
| 2 | 提炼与规则协调质量 | 不漏有效要求，不把单次要求或未采纳建议泛化；复合要求拆分，重复/补充/替代判定可追溯 |
| 3 | contract 持续演进 | 在明确开启的工作范围内，用新交互与已有规则比较；重复合并证据，新增和变更形成差异草稿；确认后新版本生效 |
| 4 | 新实例真正可执行 | contract、skill 依赖、固定资料、新输入可取得；目标 Agent 确实读取有效工作包，未继承旧实例数据 |
| 5 | 记录与跨执行者接力 | 漏采、重复、修正、恢复、来源绑定正确；换执行者仍继续同一项工作；实际读取回执和产物验证接手 |
| 6 | 审阅与日常操作体验 | 首次完整查看，后续聚焦变化；减少重复确认，来源按需展开；桌面操作短、清楚、状态真实 |
| 7 | 生命周期与数据可靠性 | 中断重启、离线重试、取消、删除、版本更新、资料损坏、协议升级不破坏已确认工作 |
| 8 | 成本、性能与发布体验 | 在前述质量基线上减少冗余调用、上下文与等待；验证打包、升级、凭据与诊断体验 |

顺序是默认优先级；基线若发现数据丢失、错误执行或主流程阻塞，先修该问题。界面与性能问题在其所影响的功能轮次顺手处理，不等到最后积压。

## Loop 规则

每轮：选择具体问题 → 给出收益假设与失败用例 → 完成一个改动 → 优先端到端验证 → 记录收益与回归 → 提交可用版本 → 选择下一项。不能通过删除失败样本或改写预期抬高成绩；参与过调参的样本不再当作盲测。每轮保留可续跑状态，额度接近上限前提前保存，不等耗尽才整理。

没有新增业务案例时，继续用已有授权真实记录回放和受控变形检查机制，并把接下来确实发生的 Worket 开发/修复过程作为可选自用案例。自用案例的选择、记录范围及验收标准须明确；不得自动导入无关聊天或改变参与改进设置。当前会话本身可讨论产品要求，但不能靠模型自行批准新业务需求来制造通过率。

工程可靠性、模型语义质量和真实用户收益分别报告。自用开发闭环可证明开发场景，不能代替视频等业务效果验证。额度作为持续工作的上限；后台模型 API 调用另记次数与 token，不把 Codex 额度与供应商费用混为一谈。此计划未创建后台定时任务，也未启用自动发布 contract。
