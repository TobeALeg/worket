# Worket 问题反馈与诊断日志设计

日期：2026-10-08。状态：设计草案，尚未实现；用户已选择每次反馈确认并附日志。

用户遇到故障时，应能在 Worket 内描述问题、添加截图，并在授权后由应用自动附上诊断日志。管理员收到一份关联完整的问题报告，能判断操作停在哪一步，而不必让用户找文件、复制终端输出或重新做一遍工作。

诊断记录只描述 Worket 如何运行，与 WorkRecord、Source Archive 和“参与改进 Worket”的工作内容采集分开。已有改进授权不授予诊断上传权限，诊断授权也不允许读取工作正文。

## 当前基础与缺口

客户端已有统一应用入口、服务连接、用户与设备身份、后台请求编号和管理员页面，可以沿用这些基础设施。目前没有统一落盘的客户端诊断日志、截图反馈入口或问题报告收件箱。后台已有模型请求元数据，但不能单独解释“点击没有反应”发生在客户端哪一步。

源码依据：[应用入口](../../src/main.ts)、[服务请求](../../src/ai-service/client.ts)、[用户与设备身份](../../server/admin/store.mjs)、[后台请求记录](../../server/service.mjs)。现有后台禁止把请求正文写入运行日志，见 [服务运行约定](../../server/README.md)。

## 用户提交流程

1. 应用菜单增加“反馈问题”；明确的失败提示旁提供“反馈此问题”，带入出错时间和操作类型。界面错误未被程序识别时，用户仍可从菜单提交；原生应用菜单提供同一入口，主面板无响应时可启动独立反馈窗口。
2. 打开紧凑的反馈页面：一个“发生了什么？”文本框，提示用户说明刚才的操作和预期结果；“添加截图”支持文件选择、粘贴和拖入，显示缩略图并可移除。提供“截取 Worket 窗口”，只在点击时截取指定应用窗口，先预览再加入。
3. “附上诊断日志”初始未勾选。首次勾选时在原处说明范围和保存期限，不另开权限弹窗。“查看发送内容”展开日志摘要、时间范围、事件数量、大小与完整脱敏事件；用户可以取消附日志，仍提交文字与截图。
4. 点击“发送反馈”固定本次报告及授权范围，自动整理所选日志并上传。只有收到后台完整接收回执后显示“已收到”和报告编号。
5. 网络不可用时显示“尚未发送，联网后自动发送”，提供“立即重试”“取消发送”“导出诊断包”。取消会移除未发队列；导出前确认同一发送范围。

正文或截图至少有一项，正常反馈入口不要求用户填写版本、系统、日志路径或技术字段；这些由应用填入。关闭页面保留本地草稿，只有点击发送后才允许后台传输。成功后在“我的反馈”可查看报告编号、处理状态和删除操作。反馈描述与截图可能含敏感信息，发送前显示：“请检查文字和截图是否包含不想分享的内容。”

沿用当前暖黄纸质面板、返回方式和控件规格。主页面只放正文、截图、附日志选择及发送按钮；日志细节按需展开。

## 本次提交授权

用户已选择“每次反馈确认并附日志”。确认仅覆盖本次冻结报告，允许断网恢复后重试同一份内容，不允许继续收集新事件追加上传。一旦发送，后续勾选变化不改变正在传输的包；用户需取消原发送、重新编辑并确认。

授权绑定接收服务、用户、设备和范围版本；服务地址或用户身份变化后停止旧队列，不把原报告发给新目的地。取消发送丢弃未发报告；已接收报告需单独删除。截图始终由用户主动选择，不自动截屏、录像或读取剪贴板；仅在用户执行粘贴动作时读取所粘贴图片，未提交草稿不发送。

首版不提供“一次授权后持续自动上报”。故障捕获只固定本机现场，不能自行生成远程报告；以后增加持续上报须另行讨论并独立授权。

## 记录哪些诊断信息

| 信息 | 记录内容 | 边界 |
| --- | --- | --- |
| 运行环境 | Worket 版本、构建标识、系统版本、架构、进程类型、运行会话编号 | 不记录用户名、设备名称、完整目录或其他应用清单 |
| 操作轨迹 | 稳定的操作名、步骤、开始与结束、耗时、成功或失败 | 不记录输入正文、聊天标题、点击坐标、逐键输入或全量鼠标移动 |
| 故障信息 | 内部错误码、类别、经过处理的堆栈、必要的状态枚举 | 不直接记录原始 Error.message、console 参数、第三方输出或响应正文 |
| 服务关联 | 本地 traceId、服务 requestId、接口模板、状态码、耗时 | 不记录 Authorization、Cookie、恢复码、请求体、URL 查询或供应商密钥 |
| 工作关联 | 报告内的随机工作代号、步骤所需计数与状态 | 不上传 WorkRecord、Source Archive、附件正文或工作数据库；外部会话 ID 不自动发送 |
| 用户材料 | 主动填写的文字与所选截图 | 在报告里单独标记为用户提交，不能宣称已经自动脱敏 |

采用按事件类型定义的字段白名单，在采集时处理，再在生成报告和服务端接收时复核。未知字段拒绝入包；自由文本不靠一个通用正则保证安全。路径去除用户与项目目录，只保留 Worket 模块和行号；无法安全处理的堆栈帧省略并标明。服务关联编号须校验格式与长度，不能把外部原文塞进编号。

例如“选择 Codex 后没有反应”，应能看到：点击交接 → 选择执行者 → 准备工作状态 → 请求打开应用 → 等待接手确认。每一步共享同一 traceId。打开请求返回成功只证明系统接受了请求，不证明目标窗口已打开或执行者已经接手；没有后续确认时保留“等待确认”。

## 本地日志与故障现场

应用启动即记录低成本的结构化运行事件到本机，无需先开上传授权。建议默认轮转保留最近 7 天，轮转文件与未提交的故障快照总计不超过 20 MiB，先到任一限额就清理旧文件；参数集中配置。启动、退出、连接、记录、同步、交接、沉淀、更新以及诊断模块自身故障都应有对应步骤。高频轮询合并计数，同类连续故障合并本地快照并记录次数，避免日志掩盖实际故障或拖慢应用。

故障被识别时冻结出错前 10 分钟以内的相关轨迹、错误事件与在途操作摘要；长操作补充开始和最近步骤，不强行复制完整历史。手动反馈默认选最近 10 分钟，也可选择仍在本地保留范围内的发生时间，明确显示实际覆盖范围。日志不可用、已过期或被截断时照常允许提交，并向用户与管理员注明缺口。

捕获主进程异常、渲染进程错误与退出、受控任务失败及操作超时。主进程崩溃前只尽力落盘，不等待网络发送；下次启动发现未正常退出标记时提供恢复反馈，由用户确认是否提交。强制结束、断电和崩溃无法仅凭标记区分，显示“上次未正常退出”，不臆断原因。用户此前已经确认发送、但尚未收到回执的报告可以在重启后重试，重启中新捕获的故障不能借用该授权。原生崩溃转储暂不纳入首版。

日志目录使用当前 dataDirectory 下独立的 diagnostics 目录，待发报告与轮转日志分开。目录权限 0700，文件 0600；这是本机访问限制，不宣称磁盘加密。写入、清理或日志读取失败不能阻塞原有记录、交接与沉淀，也不能反复触发诊断上报。

## 报告结构与可靠发送

一份报告包含固定的 reportId、发生时间、环境信息、可选描述、截图清单、脱敏事件、授权范围与版本、目的地身份和接收回执。注明日志范围是用户选定时段还是已捕获故障现场，所有报告均由用户主动提交。traceId 从用户动作开始贯穿渲染器、主进程及请求；后台返回 requestId 后与 traceId 关联。请求尚未到服务端也能靠 traceId 定位本机步骤。服务器只在同一授权主体内解析关联请求，不能凭编号读取其他用户的元数据。

建议限制：文字最多 4,000 字；最多 3 张 PNG/JPEG 截图，每张 5 MiB；脱敏日志最多 2 MiB；整个上传最多 18 MiB。限制在客户端和服务端同时执行，超限明确提示，不静默删截图。图片验证真实格式、解码尺寸与像素上限，重新编码去除 EXIF；截图内容仍由用户检查。原文件名不发送，使用报告内编号。

发送模块冻结不可变包并计算文件 hash，使用 reportId 幂等提交。后台接收元数据与附件后核对清单、大小和 hash，全部完整才提交报告并返回回执；重复提交同一包返回同一回执，编号相同而内容不同则拒绝。客户端断线或丢失回执后可以安全重试。未完成上传不可出现在已收到列表中，临时附件 24 小时后清理。

待发队列重启可恢复，重试使用退避并限制次数；永久拒绝、目的地不匹配或授权撤回时暂停或取消，不能无限循环。未发送包最多保留 7 天、总计 50 MiB；到期清除并在发送记录显示“未发送，已到期”，超过容量暂停加入而非静默挤掉已提交反馈。手动草稿使用相同到期策略。取消发送时取消后续请求；已到服务器的内容不能靠终止请求撤回，应显示已接收或接收状态待核对，并提供删除。反馈上传失败本身只落本机日志，不递归生成报告。

后台为问题报告单独配置单设备与全局上传限额，拒绝时明确说明，不使用模型额度拦截反馈。反复点击同一发送按钮复用当前报告，修改内容后重新确认生成新报告，避免重复提交与幂等内容冲突。

## 管理员如何排查

沿用私有管理员后台，增加“问题反馈”收件箱，不自动创建公开 GitHub issue。列表显示版本、发生时间、用户与设备、问题摘要、操作类型、错误码和处理状态，支持按版本、错误签名和时间筛选。

详情按顺序展示用户描述和截图、操作时间线、失败或最后未完成步骤、同主体关联的后台请求元数据以及完整脱敏日志。管理员能区分“截图显示的问题”“用户认为发生了什么”“程序实际记录了什么”，不能把没有异常日志解释为用户没有遇到问题。

处理状态为“待排查 → 排查中 → 已解决”，另有“待补充”。管理员可记录内部备注、关联同类报告和修复版本。用户的“我的反馈”只显示公开处理状态及面向用户的说明，不暴露内部备注、其他用户报告或凭据。联系邮箱为可选项，不依赖用户填邮箱才能排查；首版不发送邮件或其他外部消息。

后台建议完整报告保留 30 天，包括描述、截图、日志和内部备注。用户可删除自己的报告，管理员也可删除；删除同时清理附件、待处理临时件和关联索引，重复上传不得复活已删除报告。删除保留最小幂等墓碑至待发包最大生命周期结束，不保留正文；备份保留与恢复后的删除重放须在上线前落实，不承诺无法执行的即时备份擦除。不得把这批报告自动转成 90 天改进样本。

## 模块与数据流

| 模块 | 单一职责 |
| --- | --- |
| diagnostics | 类型化事件、字段白名单、关联轨迹、轮转与故障快照 |
| problem-reports | 草稿、用户材料、本次授权、冻结报告、队列与发送状态 |
| report-client | 经现有服务身份发送报告，处理幂等回执、恢复和删除，不调用模型 |
| server reports | 身份与归属校验、限流、附件检验、完整接收、留存与删除 |
| admin reports | 收件箱、时间线、筛选、处理状态与备注 |

客户端队列状态：草稿 → 已授权待发送 → 发送中 → 已收到；断网回到待发送，永久失败转为需处理；取消、到期或删除不再重试。发送状态与管理员处理状态分开，发送成功不等于问题解决。

拟新增报告上传、本人列表与详情、本人删除接口，归入现有 /v1/ 服务入口，沿用 TLS、用户与设备身份、令牌续期及撤销检查；报告 API 与模型调用额度分开。旧后台通过能力声明识别是否支持报告，不支持或身份连接不可用时保留本地报告并允许导出。报告发送不能依赖模型配置成功或消耗模型调用。

数据流：渲染器动作 → 主进程诊断事件 → 本地轮转文件；用户反馈并确认发送范围 → 固定报告 → 持久化发送队列 → 完整接收回执 → 管理员收件箱。渲染器只能发送预定义事件，主进程验证事件与截图输入，不能通过任意 IPC 参数访问其他本机文件。

## UI 设计候选

2026-10-08 已制作 [可交互原型](../../research/prototypes/problem-feedback/README.md)，位于独立分支 `codex/prototype-problem-feedback`；沿用实际客户端主题、品牌栏、返回方式与固定底部操作。三种候选分别是单页反馈、工作详情内的反馈抽屉和分步确认。助手推荐单页版，用户尚未确认选型。

原型包括截图预览与移除、默认未勾选的本次日志授权、按需查看日志、发送结果、断网待发、我的反馈与删除确认；管理员页将用户描述及截图与操作时间线并排展示，处理状态和内部备注单独管理。正常填写、添加截图和展开授权说明在 410×660 面板内无需滚动；窄窗保留底部发送按钮。

发送、回执、窗口截图与管理员状态均使用本地演示，不连接生产服务或真实工作数据库；原型验证不代表正式采集、授权、可靠上传或服务端留存已实现。截图添加、日志预览、成功/离线/缺失日志、删除及窄窗交互已在浏览器检查。

## 首版验收标准

- 同事电脑上“点击交接无反应”提交一次反馈后，管理员可看到所选截图、描述、版本、操作时间线和最后已确认步骤；反馈入口自身无响应时，可从原生应用菜单打开独立反馈窗口或导出脱敏诊断包。
- 未授权时没有诊断上传；本次确认只允许发送与重试冻结报告，不追加新日志；取消、换身份或换服务能阻止队列继续发送。
- 用包含令牌、恢复码、用户目录、聊天正文、文件正文和自由格式错误消息的样例，检查本地事件、上传包与后台存储均未漏入这些内容；用户主动提交的文字和截图单独标记。
- 断网、附件上传中断、回执丢失和应用重启后，报告不丢失、不重复入库、不假称成功；日志缺失、磁盘满和截图超限仍可提交有效的文字反馈。
- 主进程异常退出后可恢复已经落盘的现场，未正常退出不误称崩溃；重复故障快照受容量约束，诊断故障不递归上报。
- 删除会清除报告内容与附件，删除后重试不会复活；其他用户无法读取、删除或借请求编号关联该报告。

先完成客户端诊断、反馈提交、可靠接收及管理员查看的闭环，再验证撤回、崩溃恢复和清理。此设计不改变 WorkDefinition、WorkInstance 或 Source Archive 的语义；实现完成后再更新产品与架构现状并记录桌面与服务端验收。
