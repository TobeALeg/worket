# 长记录样本的增量同步与预算

2026-09-23。完整视图逐条重发会使传输随历史长度平方增长，也更早消耗样本事件限额。

## 增量与恢复

新记录上传 schemaVersion:3，能力 recordingViewSchemaVersions:[1,2]。第一份或升级缺少本地基线时发送完整 RECORDING_VIEW；随后用 baseSequence 指向前一已排队视图，只发送变化的条目。本地 recording_views 保存完整基线，推进基线与排队增量在同一事务中完成。重启不会跳过尚未发送的中间变化，幂等事件 ID 防止“接收后响应丢失”的重复计数。

后台从最新完整检查点起按序重建，增量必须精确接续；乱序可在补齐后恢复，缺链或同序号冲突仍不提供当前内容。未来完整检查点可重新确立完整基线。消息本体、历史修订与可观察缺失状态仍保留，未通过删除历史降低成本。

新客户端要求能力 2 才发送记录队列，后台兼容原 v1/v2 与完整视图。旧后台不会收到可被误解的新增量格式。状态解释和用户授权范围不变。

## 预算

记录样本同时限制最多 10,000 条事件与 20 MiB 原始事件 UTF-8 正文字节，以先触及者为准；包括消息分片和视图，不等于 10,000 条聊天。沉淀/复用样本仍沿用 1,000 事件限额，用户 1,000 样本与 90 天保留期不变。达到上限仍明确停止该记录样本，保留本地原始工作，不静默截断为成功。

sample_usage 按事务维护接收字节，旧样本首次新写入时按已有证据初始化；相同事件重试不再收费，失败不推进，删除/过期清除计数。该表是可重算的派生元数据，不改写旧事件。兼容回滚时旧程序忽略此表。

本轮优化传输及待发队列字节，没有减少正常逐条上传的 HTTP 请求数，也没有宣称本地全档扫描/基线序列化已线性化。长记录界面渲染、批量传输与本地处理成本仍可继续测量。
