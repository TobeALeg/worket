# Working Contract 持续提炼与复用：下一轮方案

日期：2026-09-22。状态：供用户评审的方案；未修改提取算法、正式 Gold、领域模型或发布流程。

## 目标与产物

用户最终目标：Worket 从用户和 Agent 的真实交互中持续提炼有用要求，形成可复用 working contract；下一次只需选择 contract、提供新脚本并使用 HyperFrames skill，即可创建新 WorkInstance 并完成交付。

working contract 在本方案中由现有 WorkDefinition 承载，不增设同义实体。WorkState 仍负责这一次工作的状态；WorkRecord 保存发生过的事情。目标是减少下一次重复解释、修正和检查，而不是增加摘要长度或只提高抽取分数。

## 1. 先分清适用范围，再决定是否重复

每个候选至少表达：要求、适用条件、来源及上下文、用户是否采纳、当前是否有效、与既有规则的关系。试验中作为内部结构保留，不立即扩建正式数据库。

归入四个去向：

| 去向 | 判定原则 | 视频例子 |
| --- | --- | --- |
| 可复用规则 | 有明确长期意图，或在限定工作类型中有足够证据支持 | 每期科普视频交付对应封面；动画表达与相关口播同步 |
| 条件规则 | 保留完整适用条件，不能省掉条件后升格 | 科普动画使用已确认片尾；特定平台交付采用对应裁切规范 |
| 本次输入或例外 | 只影响本次实例，仍可对当前执行很重要 | 本期脚本、48 秒场景、这次临时换背景音乐 |
| 待确认候选 | 有可能有用，但长期范围或采纳依据不足 | 一次“放大一点”能否成为后续固定规格 |

“通用”指在明确工作类型与条件下可复用，不等于适用于用户所有工作。反复出现只能增加证据，不能单独证明长期意图；用户明确说“以后每次”时，一次表达也可以充分。

对“48 秒处与口播同步”：实例层保留具体修正，规则层可提炼“表达口播含义的动画，应随相应口播呈现”。今天的用户澄清是新增范围证据，应记录其日期，不能伪造为历史原句已经明确表达了同样范围。

抽象后仍须可执行：保留明确的 50 words、3:4、片尾语速 1.3 等有效要求与条件，不能统一改写成“文案简洁、视觉美观”。也不能把某处重叠问题泛化为“所有视觉元素绝不允许重叠”，从而禁止合理遮挡和图层构图。

## 2. 重复项不新增规则，但保留来源和新信息

生产去重只能读取已授权原文、候选要求和现有 contract，不读取 Gold 或人工答案。

语义协调输出五种操作：新增、合并证据、补充规则、替代规则、暂不进入 contract。每次合并都要指向最终保留的规范条目；程序检查目标存在、不存在循环合并和整组全删。模型判断语义，程序保证关系完整。

- 同一范围、条件和含义均相同：保留一条正文，追加来源，不让用户再确认重复文本。
- 新增验收细节或更严格边界：补充已有规则，不能只因主题相近判为重复。
- 120 words 改为 50 words：同一范围内的替代，保留变更记录；不是重复。
- 默认固定 BGM 与“这次换音乐”：本次例外，不改默认，也不当作冲突删除。
- 不同工作类型规则不同：分别保留适用条件，不按最后一条覆盖所有工作。
- Agent 提议与用户批准：即使文字相同，批准仍改变采纳状态；不能作为无信息重复丢弃。

约束与验收可以引用同一规则，无需重复写同义段落；如果验收增加了可操作的检查标准，应保留其增量。执行包按需要输出，审计引用保留在背后。

## 3. 持续学习采用规则增量与版本

建议流程：

`已授权的新交互 → 候选及证据 → 范围/采纳/有效性协调 → 与现有规则比较 → 变更草稿 → 确认后的 Definition 新版本 → 新实例`

本轮先完成一次可复用 contract 的提炼和执行包验证，再实现自动增量触发。长期方案允许用户对某类工作开启持续学习；这与当前“主动点击沉淀”不同，属于待评审的产品变化，不在本轮静默启用。

纯重复仅合并证据；用户只需关注新增、改变适用范围、冲突与真正不确定的规则。首次展示完整 contract；后续展示变更前后及其适用范围，避免反复通读全文。确认内容、自动判断、是否正确按顺序排列，分歧时再展开证据。

新版本影响以后创建的实例；已有实例固定原版本。新实例中的临时覆盖不自动写回长期 contract；用户明确说“以后都这样”时，生成长期规则变更。含糊冲突保持待确认，避免误执行。

## 4. 下一次只提供新脚本的实际前提

contract 保存稳定目标、工作范围、输入角色、交付物、约束、条件、验收和已确认固定资料；HyperFrames skill 提供制作方法；本次脚本提供新内容。无须将 skill 全文复制成用户要求。

首次建立 contract 时，要把“这一版品牌联系卡”“固定的背景音乐”“模板动画”等口头引用落实为可访问、可校验的固定资料。否则只给 contract + skill + 脚本仍不足以执行。固定资料属于 contract 的依赖，不能靠 Agent 记住旧路径或旧对话。

执行包应包含：固定 Definition 版本、适用规则、新脚本与必要参数、固定资料、skill 依赖和本次验收项。不继承旧脚本、旧输出、完成状态或临时授权。日期等参数可确定性生成；已有确认默认值无需重复追问，真正缺失的关键输入再询问。

验收还要检查：调用新实例入口后，这些内容确实进入实际发送给 Agent 的包，而不是只存在于模型中间 JSON。

## 5. 最小实现与对照

当前 `server/workflow.mjs` 已有分块提取、协调与泛化及 INSTANCE/REUSABLE/UNCERTAIN，不另建一套抽取系统。主要缺口是中间结果未明确保存采纳/有效状态与条件；聚合阶段只接收摘要和事件身份，缺少核对范围所需的原句上下文；重复判断未形成有保留目标的操作。

建议按可定位收益的顺序试验：

1. 冻结已有 E0、Gold 和人工裁定。建立 D 轨道 Gold v2 草稿，把历史要求、今天澄清的范围、评审新增要求分开。只请用户确认变化，所有对照使用相同版本评分；Gold 不进入被测提取器。
2. 保留现有模型与调用结构，先改提示词及中间表达，使范围、条件、采纳、替代、去重保留目标显式化。得到基线 A 与最小改动 B。
3. 单独测试为协调阶段补回候选引用的原句、相邻确认及替代上下文，形成 C；记录额外 token、成本、延迟，不把证据补齐与提示改动混为单一收益。
4. 只有上述简单方案仍不够时，增加一个不读取 Gold 的语义审核阶段，与最佳简单方案比较。不能因为评测模型能找重复，就预设线上多调用一定值得。
5. 输出完整中文 contract 草稿、适用范围、合并/排除明细及真实新实例执行包，再进入用户确认和新脚本执行验收。

相关落点：`server/workflow.mjs`、`src/contracts/definition.ts`（如确需扩展契约）、`src/definitions/work-package.ts`、既有 DefinitionDraft 审阅与 `evals/extraction/`。WorkState 去重可另做同实例改进，但不能代替这轮 Definition 目标。

## 6. 验收标准

校准回归：每个合并条目有保留目标，关键要求不因去重丢失；规则中的数字、条件、否定和采纳状态正确；无旧实例参数、失效规则和未批准 Agent 建议混入有效 contract。以语义单元和最终执行包评分，不能靠把多条要求拼成一条来降低表面重复率。

先由用户确认 D 轨道参考答案中的范围差异，随后冻结比较。已见的两份案例只作校准；另用未用于调参的新输入检验泛化。现有四份试点保留记录存在操作者先验暴露，不称严格盲法；用于调参后不得继续称保留集。

重点报告：可复用规则严格覆盖、错误泛化、重复残留、去重导致的丢失、人工修改/审阅时间、调用成本与失败率。对自动判为正常的规则也作人工核对；只看风险项时继续报告下限，不声称全量精确率。

最终必须完成至少一次：选择 contract → 输入未见的新脚本 → 新 WorkInstance → Agent 使用 skill 与固定资料制作 → 用户验收成片及其他交付物。再比较同一执行者、skill、脚本与资料条件下，有无 contract 的重复说明、返工与总投入。首次真实通过只证明闭环可用，多次不同输入的对照才支持稳定收益。

本轮方案交付不等于算法优化、上线或新视频验收完成。
