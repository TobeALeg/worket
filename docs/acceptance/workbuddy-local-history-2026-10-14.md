# WorkBuddy 接入验证与兜底方案（2026-10-14）

## 正式接入

核实来源：[Open API](https://open.workbuddy.cn/docs/openapi)、[第三方应用](https://open.workbuddy.cn/docs/third-party-app)、[连接器](https://open.workbuddy.cn/docs/connector)。官方开放本地助理状态/消息/历史及云端任务；文档没有证明可遍历用户任意桌面聊天。需要开发者应用、clientId/clientSecret 与用户 OAuth；密钥不得放在客户端。本轮为文档与能力范围验证，没有注册应用、取得凭证或调用授权 API。不能将“存在查询消息接口”当作当前 HISTORY 适配器的等价替代。

本机 5.8.2 的内部 Extension 加载要求签名安装记录与完整性验证；直接复制 worket-capture 目录不满足加载条件。本轮不关闭签名验证、不修改 WorkBuddy 安装包、不读取登录 token 代替正式授权。故障已在 5.7.7 出现，未证明限制首次引入于 5.8.2。

## 本地只读路线与选择

当前账号 SQLite 索引有 91 个未删除本地会话，64 个存在对应 JSONL，27 个缺少本地正文。只读扫描验证 64/64 可解析，共 979 条可见文字/显式附件事件；其中一份只有内部 Hook 状态，投影为零条可见事件。最近的 Word 转换会话含 2 条用户消息、12 段助手文本、2 条显式附件引用，最终答复标记与此前原应用可见答复相符。没有据此宣称全部会话历史完整。

选择本地路线作为本次默认读取方式：可直接验证、无需额外账号授权、无需让外部应用运行我们的扩展。代价是存储格式仍可能变化，缺少本地正文不能恢复，删除/分支/压缩不作为权威历史处理。解析失败保留真实错误，绝不返回“完整空历史”。读取范围在历史面板可见。活动请求延迟导入助手文本；只读 SQLite 事务与文件读取前后检查减少并发写入的不一致。

## 能力隔离

新增 inspectDelivery，可读取但不能交付、可交付但不能读取独立表达。WorkBuddy 的交付预检只查询系统 URL 注册入口；本地读取失败不再挡住目标交付。源工作正在记录时仍要求刷新来源成功，防止悄悄丢掉最新上下文。MCP 工作包读取、Hook 实际消息和交付回执继续分别验证，不把打开任务当成发送成功。

## 如果其他本地 Agent 也限制接入

后续用户已明确不考虑 RPA，只保留人工接手兜底。下表及 RPA 讨论保留为当时的方案评估，不代表实施计划；当前产品范围以 product.md 为准。

按能力选路线，而不是给整个应用贴“可用/不可用”标签：

| 层级 | 适用能力 | 证据与失败处理 |
| --- | --- | --- |
| 官方 API/授权连接器 | 读取、交付、增量通知 | 仅使用已授权范围；检查分页、消息身份、接手回执 |
| 本地只读记录 | 已落盘正文与增量 | 显式覆盖范围；拒绝损坏；不推断未观察到的删除 |
| 原应用导出 | 用户选择的历史快照 | 保存来源与时间；区分快照与持续同步 |
| RPA：可访问性树优先，视觉识别辅助 | 打开聊天、读取已加载正文、准备草稿/导出 | 核验应用、窗口与聊天身份；界面变动后重新观察；无法确定则停下 |
| 人工选定内容/复制工作包 | 最小可继续流程 | 用户确认角色与会话；保留已有工作身份；不宣称完整采集 |

RPA 在 API 受限但界面仍开放时可行。macOS [AXUIElement](https://developer.apple.com/documentation/applicationservices/axuielement)、Windows [UI Automation](https://learn.microsoft.com/en-us/windows/win32/winauto/entry-uiautocore-overview)提供语义化控件访问。此次 Computer Use 能查看 WorkBuddy 聊天、提示与输入框，并完成正常退出/重启；这是原应用可操作的证据，不代表 Worket 自带 RPA 已实现。

未来实现必须将桌面操作串行化且可见，用户随时取消；绑定明确窗口/会话，不能猜最新聊天；优先复制正文/导出，OCR 只作次级证据；虚拟列表、折叠/分支和未加载历史不能计作完整。填入草稿与发送分开，自动发送需明确授权并核验新增用户消息；状态不明禁止重试发送，防止重复任务。权限撤销、锁屏或应用不暴露控件时转人工。若接口、文件和界面全部不可读，RPA 也没有保证，手动选择/导出仍是最后兜底。
