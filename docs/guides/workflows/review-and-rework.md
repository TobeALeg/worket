# Worket 验收返工操作指南

任务标识：WK-REWORK-1021-B

读者：已经开展流程、需要验收成果并处理上游修订的用户。

## 先分清四件事

Worket 里有四个容易混在一起的动作，请分开看：

- **发送**：打开外部应用只是打开，不等于已发送或已执行，必要时要在执行者里确认发送。
- **执行者报告**：执行者说完成，是它的说法，不是你的结论。
- **成果登记**：执行者用 `submit_workflow_outputs` 提交，或你在界面点「关联并提交成果」，文件固定后成为**待验收**项。
- **验收通过**：只有你逐项验收，下游才放行。文件存在不等于通过。

## 提交待验收

执行者在当前工作包里拿到本轮独立目录和输出键，把成果写进该目录后用 `submit_workflow_outputs` 提交；也可由你在界面手动关联并提交。提交只做一件事——把文件或文本固定下来，不自动放行下游。

「待验收」只列当前轮次，显示运行、版本、节点和轮次；暂停项先恢复。

## 退回修改

验收不通过时选「退回修改」，**必须填写修改意见**。系统会创建新轮次和新 WorkInstance，旧成果和验收历史保留，方便回看当时为什么退回。旧轮的迟到提交不能覆盖当前轮，执行者要写新目录，不要在旧目录里改。

## 重做这一步

不需要改上游、只是这一步想再来一次时，用「重做这一步」，同样创建新轮次，规则与退回修改一致。

## 上游改了：影响范围与采用新版

上游新版验收通过后，**已开展的下游不会自动换用新成果**，会继续采用旧成果。这是有意的：整套流程开展时会固定本次输入，文件按内容快照和 SHA-256 保存，原文件变化不静默替换已开展的下游输入。

要换新版，按这个顺序做：

1. 先查看**影响范围**。当前按依赖闭包保守计算，内容相同也不会自动省略重做，所以范围可能比你预期大，先看清楚。
2. 明确确认**采用新版**。
3. 确认后，系统为依赖该节点的后续工作建立新轮次，这些新轮次才使用新成果。

**不受影响的部分**：不同运行互不更新成果，另一运行保持原样；独立分支也不受影响，仍保留旧版本。

注意：确认采用新版之后，受影响节点只是**变为可开展**，不是说成果已经存在、已经在待验收里等着你。这一步常被跳过，务必区分。

## 一条可照做的操作路径

上游某节点被退回、你改完并重新验收通过，下游想用新成果：

1. 在上游新轮次完成修改并提交，逐项验收通过。
2. 打开影响范围视图，确认哪些下游工作会被波及。
3. 确认**采用新版**。
4. 在变为可开展的受影响节点上点「**开展工作**」，选择执行者。
5. 在执行者中**确认发送**（打开外部应用不等于已发送），让实际工作真正发生。
6. 由执行者在新轮次目录**实际生成成果**并提交（执行者调 `submit_workflow_outputs`，或你在界面关联并提交成果）。
7. 回到「**待验收**」逐项核对新提交的成果，验收通过才放行下游。

第 4–6 步不能省，也不能反过来理解成「新轮次一建立就有东西可验收」。成果要人做出来并提交，才会出现在待验收列表里。

## 并行与汇合的一个具体例子

假设两个独立节点分别产出**正文**和**清单**，下游**交付索引**节点汇合两者。

如果你只修订了正文、只确认采用正文的新版：

- 依赖闭包里只有**交付索引**，所以它拿到新轮次，需要重做——重做时汇入的是新正文和清单的现有成果；
- **独立清单**不在依赖闭包内，没有建立新轮次，成果原样保留；
- **另一运行**与该流程互不更新，也保持原样。

即：只改正文，就只重做索引，清单和另一运行都不动。反过来，如果改的是清单，受影响的就是索引，正文那一支不动。汇合节点之所以要重做，是因为它的输入变了；没被波及的并行分支不需要陪着一起跑。

## 边界提醒

- 暂停只停止新的准备与交付，不保证终止已在外部执行的工作。
- 当前没有无人值守发送、动态分支/循环、跨设备同步、执行容量队列或操作系统级隔离；工作包不是操作系统沙箱。
- 节点要等全部前置工作验收通过才可开展。
- 固定文件沿用 50 MiB 单文件上限；常见文本文件 256 KiB 内可在应用中预览，其他文件在本机打开。
