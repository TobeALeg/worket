# 你在这轮测试中要做什么

**你负责真实要求、真实授权、真实交付判断；Codex负责找代码、写测试、调Agent、跑批次、计账和整理结果。** 你不需要自己写测试代码，也不需要天天在4个Agent之间传话，只对接总控。

## A. 开始时先给一小包，不必等所有材料齐全

给总控本地 Worket 仓库的位置，并选择一类你真的反复做的工作。默认候选是“根据素材制作视频内容方案/brief”，不是要求你一定测完整视频渲染。

第一包只需要：

| 你提供的内容 | 合格长什么样 | 不足时怎么处理 |
|---|---|---|
| 1份真实历史工作 | 完整对话或明确授权的会话ID；包括你的修改、否定、例外 | 只有总结不足以核验提炼；先跑合成测试 |
| 该工作的必要附件与最终成果 | 可读取的文件副本/明确允许访问的资料，不只失效链接 | 缺失单列，不让Agent猜 |
| 你现在会如何再次做这类工作 | 现有Skill、模板、旧会话、手工说明等真实最好方案 | 没有文档可用口头演示，Codex记录并让你确认 |
| 目标与验收规则 | 做给谁、交什么、不能出现什么、怎样算能交付 | Codex整理8—12条，你修正；不让它独自定义你的品味 |
| 数据与费用选择 | 哪份材料可发给哪个服务；可用测试账号；总预算与是否允许改集成 | 默认不读私人历史、不外发、不调用收费模型 |

不发送API Key、SSH私钥或auth.json。只告诉Codex应使用哪个已配置服务/本机凭据位置，由它使用安全方式接入，不打印正文。

你给过的信息不应被反复询问。总控先自查环境与现有文件，再把真正缺的决定放入HUMAN_INBOX。

## B. 正式阶段补齐的材料

历史记录目标6份：2份调试、4份封存；尽量两位作者。新的输入目标6份，不能提前用来改定义，其中包含1个不应套用这一定义的边界任务。没有足够真实工作就减为试点并注明样本，不让Agent伪造。

给每份源一个简单标签，例如“D01 调试/可以发送到指定服务”“T01 封存/只允许本地”；具体分组、哈希、JSON由Codex处理。

涉及公司、客户、同事记录时，确认你有相应使用与外发授权。无法确认的内容先去除或换成你拥有的任务；脱敏不自动解决权限问题。

要形成非创始人价值证据，邀请3位有对应工作的人；自然使用观察可3—5人。现阶段没有人也能先做机制与内部验证，但不能称外部验证。

## C. 你必须亲自确认的6类事项

| 关卡 | 你看到什么 | 你回答什么 |
|---|---|---|
| H0 数据/账号/费用 | 具体源文件、接收方、用途、动作、预算、是否改hook | 批准明确范围，或删掉/限制某项 |
| H1 试验规则冻结 | 最佳基线、任务分组、评分表、版本、阈值 | 这些规则反映真实工作，而且比较公平吗 |
| H2 候选定义 | 原始候选、来源、适用范围、待处理问题 | 哪些保留/修订/删除，哪些是你现在新增 |
| H3 桌面交接 | 所选Codex thread、目标WorkBuddy账号、待发内容 | 是否允许本次外发与继续工作 |
| H4 实际成果 | 隐去组名的产物、冻结任务卡、计时记录 | 能否交付，有何严重错误，实际人工投入是否准确 |
| H5 采用与披露 | 真实下一次任务与使用行为、准备对外的脱敏结论 | 是主动再用还是被提醒；是否允许公开这些内容 |

H0可一次批一组明确材料，不必每个请求都点。换资料、接收方、用途或预算时才重新请求。H2/H4是业务判断，不能用“已授权外发”替代。

你可用自然语言回复，例如：

> 同意H0-003列出的D01、D02，发送到表中指定的Worket服务，仅用于本轮提炼；不用于改进样本；不改全局hook。费用不超过我在授权卡确认的上限。

具体金额/服务须在卡中实际填写，不能保留模糊占位就放行。Agent保存你的真实回复，不能替你说这句话。

## D. 怎样人工验收提炼

先看原始候选，不先看已经改好的漂亮版本。逐项只回答四个问题：

1. 原文真的有依据吗，还是Agent猜的？
2. 表达的意思、角色、时间与范围对吗？
3. 这是以后复用的要求，还是只属于这一单/已被推翻/未确认？
4. 真正关键的要求有没有漏掉？

你补写的新要求标“本次新增”，不要改称“系统从历史里发现的”。不确定就标待确认，不为完成进度强行通过。修改、查来源的实际时间计入Worket成本。

## E. 怎样人工验收最终交付

总控给你盲编号，不给A/B/C。你先按冻结规则检查硬约束，再评价软质量；不要因为某个答案很像你的说话方式就默认更好。

建议的软评分初稿（正式前由你修改并冻结）：可执行与可交付40分；内容完整30分；清晰可用20分；不靠无根据假设10分。严重事实/对象/授权错误单独否决，不能靠其他分数补回来。

输出评定：可直接交付 / 修改后交付 / 不可交付 / 当前无法判断。附具体位置、需要怎样修改。形式上的文件存在与工作真的完成不是同一件事。

正式机器批次36份产物应全部进入审查账本，可分配给合格同事；你至少负责业务规则、争议与所有严重告警的最终裁定。无人审查的份数保持NEEDS_HUMAN，不由模型代签。样本小的时候不要宣称显著提升。

## F. 怎样记录你的时间

Codex准备分阶段计时卡，你只在真正开始/暂停/恢复人工操作时点击或告知。记录安装/学习、整理、审阅定义、找材料、补说明、返工、业务复核、维护；等待模型另记。

同一人的同时段不能加两遍；两个人的劳动各自计入。为了实验才做的研究评分与日常交付复核分开。事后估算必须标估算，不和直接测量混称实测。

即使后续单次变快，初次确认成本没有回收，也不能写“总体省时”。没做成的任务提前退出，更不能被算成快。

## G. 你不在场的交接怎么测

选没参与原始工作的合格同事，给新输入与允许资料，让对方先说明目标/边界/不确定项，再执行。不要在旁边一句句指导。确实要帮就帮，但记录为什么、补了什么、花了多少主动时间。

已有要求没留下导致你救场，是知识传递成本；真正出现新决策需要你决定，不应算成接手者失败。二者分开。

真实桌面接力脚本会要求你在选定Codex任务新增一轮对话，等回复完成后回终端继续。这一步必须真的发生，不能空按回车伪造。

## H. 最后你看哪几页

不必读全部技术日志。让总控给你这四页：

- 工程：哪些实际跑过、哪些失败、哪些需要Mac/权限；不要只有一句全绿。
- 价值：A/B/C质量、完成数、总主动投入与初次成本，按人/任务逐例。
- 采用：多少人有下一次机会，多少人主动再用，谁被提醒，谁失访。
- 宣称范围：可以对投资人说什么，每句话指向哪份证据；还不能说什么。

你签的是“这些业务与授权事实准确”，不是代替工程师证明所有代码没有bug。

## I. 你亲手点检产品时，按这个顺序

使用已批准的测试资料与隔离测试库，不拿日常全部记录做试验。

| 你做的动作 | 你应当看到的结果 | 应当拒绝通过的情况 |
|---|---|---|
| 选择一项工作并记录 | 内容和来源对应这项工作 | 混进另一项工作或未经选择的会话 |
| 提炼后看候选与来源 | 能找到关键要求依据，并看出未确认问题 | 全是漂亮总结却查不到证据 |
| 修改一条要求再确认 | 修改真实保存，人工新增被标明 | 刷新丢失、把你补写说成自动提炼 |
| 用不同客户/素材创建新工作 | 新实例、新输入，旧工作仍保留原状态 | 新工作带着上次客户、进度或完成标记 |
| 按新实例执行并检查产物 | 成果符合你事先确认的规则 | Agent说完成但文件缺失、对象错误 |
| 退出重开 | 定义、版本、已保存成果和状态仍可辨认 | 消失或历史版被静默改写 |
| 在测试副本中让一个引用失效 | 明确告诉你缺什么，不假装读过 | 编造引用内容或静默换材料 |
| 停止记录后继续在测试会话发言 | 新内容不再进入已停止的绑定 | 停止开关仅改变外观，实际继续采集 |

这些点检补充自动测试，不替代完整来源核验、盲评和真实人工计时。每次把“预期/实际/截图或文件/是否需要帮助”留给总控。
